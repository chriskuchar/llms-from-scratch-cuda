# Training Parameters Explained

Everything you see in the training output, what it means, and how to tune it.

---

## Data Preparation Output

```
Reached 10,000,000 token limit.
Done! Wrote 10,120,546 tokens to data/pretrain_test.bin
  File size: 0.04 GB
  Tokens per param: 0.1x (125M model)
```

| Field | Value | Meaning |
|---|---|---|
| **10,000,000 token limit** | 10M | The script stops downloading text after tokenizing this many tokens |
| **10,120,546 tokens** | ~10.1M | Actual count (slightly over because it finishes the last document) |
| **data/pretrain_test.bin** | binary file | Pre-tokenized data — each token is a 32-bit integer ID, packed end-to-end |
| **0.04 GB** | 40 MB | 10.1M tokens × 4 bytes each = ~40 MB |
| **Tokens per param: 0.1x** | ratio | You have 0.1 tokens per parameter. Chinchilla optimal is ~20x. This is a quick test, not a real pretrain |

### What data is this?

The `pretrain_test.bin` was generated by the tokenizer script pulling text from a dataset (TinyStories or OpenWebText subset), tokenizing it with SentencePiece into integer token IDs, and writing them as raw binary. The dataloader reads this file sequentially, slicing it into batches of `B × (T+1)` tokens at a time (the +1 gives us input + target for next-token prediction).

### How much data do you actually need?

| Goal | Tokens | File Size | Time (fp16, B=8) |
|---|---|---|---|
| Quick sanity test | 10M | 40 MB | ~20 min |
| Minimal pretrain | 100M | 400 MB | ~3.5 hours |
| Decent pretrain (TinyStories) | 500M | 2 GB | ~15 hours |
| Good pretrain (Chinchilla-ish) | 2.5B | 10 GB | ~3 days |

These are documented in detail in `ARCHITECTURE.md`. Quick reference:

| Field | Value | What it controls |
|---|---|---|
| **12 layers** | transformer blocks stacked | More layers = deeper reasoning, more VRAM |
| **12 heads** | attention heads per layer | Parallel attention patterns |
| **4 kv** | key/value heads (GQA) | Saves memory — 3 query heads share each kv head |

| **934.0MB** | activation memory | Temporary buffers during forward/backward (scales with B×T) |

## Training Parameters

```
Training for 100 steps (accum=1, effective batch=2048 tokens)...
```

### B (batch size)

```
B=4
```

Number of **independent sequences** processed in parallel per micro-batch.

- Each sequence is T=512 tokens long
- So one micro-batch = B × T = 4 × 512 = 2,048 tokens
- Higher B = more GPU utilization, but more VRAM
- **Tuning:** With fp16 on a 3060 (12GB), you can safely use B=8 or even B=16

| B | Tokens per micro-batch | VRAM (fp16) | Throughput |
|---|---|---|---|
| 4 | 2,048 | ~2.5 GB | baseline |
| 8 | 4,096 | ~3.1 GB | ~1.5-2x faster |
| 16 | 8,192 | ~4.2 GB | ~2-3x faster |

### T (sequence length)

```
T=512
```

Number of tokens in each training sequence. The model learns to predict each token from all previous tokens in the sequence.

- T=512 means the model can "see" up to 512 tokens of context
- Larger T = longer context window, but VRAM scales with T² (due to attention scores)
- **Tuning:** 512 is good for 124M. Could go to 1024 if VRAM allows

### accum (gradient accumulation steps)

```
accum=1
```

How many micro-batches of gradients to **accumulate** before doing one weight update.

- `accum=1`: process 1 micro-batch → update weights (current setting)
- `accum=4`: process 4 micro-batches → sum their gradients → update weights once
- Simulates a larger batch size without extra VRAM
- **Effective batch = B × T × accum**

#### How it works (step by step)

One training **step** = `accum` forward/backward passes, then **one** optimizer update — not `accum` updates:

```
zero_grad()
for i in 0..accum-1:           # accum DIFFERENT micro-batches
    micro_batch = dataloader.next()   # fresh data each pass (not the same batch!)
    forward(micro_batch)
    backward()                 # ADDS this batch's grads into the grad buffer
optimizer.step()               # ONE AdamW update on the summed gradients
```

Key points that trip people up:

- **Different data each pass.** The `accum` passes each pull the *next* micro-batch. Over one step you see `accum × B` distinct sequences. Running the *same* micro-batch `accum` times would just give `accum ×` the identical gradient — no benefit, and it would overfit those few sequences.
- **Gradients are additive.** Summing the gradients of `accum` small batches equals the gradient of one big batch:
  `∇L(batch of accum×B) = Σ ∇L(micro-batch_i)`. That's *why* accumulation reproduces large-batch training exactly.
- **One optimizer step, not many.** `step` in the logs counts optimizer updates. Each step is ~`accum`× the wall-clock of a single pass, which is why steps feel slow at high `accum`.

#### Why accumulate at all?

A single micro-batch (e.g. B=4) gives a **noisy** gradient estimate. Updating on every tiny batch makes training jumpy and forces a smaller learning rate. Accumulating to a large **effective batch** averages out that noise → a smoother, more reliable update direction. You'd normally just use a bigger `B`, but VRAM caps how many sequences' activations fit at once — accumulation buys the gradient quality of a large batch while only holding `B` sequences on the GPU at a time.

| accum | Effective batch (tokens) | Effect |
|---|---|---|
| 1 | 2,048 | Fast updates, noisier gradients |
| 2 | 4,096 | Smoother gradients |
| 4 | 8,192 | Even smoother, recommended for larger datasets |
| 8 | 16,384 | Very stable, good for long pretraining runs |

**Tradeoff:** Higher accum doesn't slow down total training time (same number of tokens processed), but each "step" takes longer and you get fewer weight updates. For a 500M token run, `accum=4` with B=8 is a good balance.

### effective batch

```
effective batch=2048 tokens
```

The total number of tokens the model "sees" before each weight update:
`effective batch = B × T × accum = 4 × 512 × 1 = 2,048`

This is what actually matters for training dynamics. Research suggests effective batches of 4K-64K tokens work well for models this size. With B=8 and accum=4, you'd get 8 × 512 × 4 = **16,384 tokens** per update — a solid choice.

### --fp16 (mixed precision)

```
--fp16
```

Enables fp16 mixed precision training:
- Weights, activations, and gradients stored as 16-bit floats (**half the memory**)
- Matrix multiplications use tensor cores (**3-4x faster** on RTX 3060)
- Master weights and optimizer state stay fp32 (for numerical stability)
- Loss scaling prevents tiny gradients from becoming zero in fp16

| Mode | Weight storage | Compute | Tensor cores | Speed |
|---|---|---|---|---|
| fp32 (default) | 32-bit | 32-bit | No | ~2,275 tok/s |
| fp16 (--fp16) | 16-bit | 16-bit + 32-bit accumulate | Yes | ~7,000 tok/s |

### lr (learning rate)

Controlled by `--lr` flag (default 1.5e-4). Uses linear warmup + cosine decay:
- **Warmup:** LR ramps from 0 to peak over first N steps
- **Decay:** LR follows a cosine curve down to min_lr
- Higher LR = faster learning but risk of instability
- **Tuning:** 1.5e-4 to 3e-4 is typical for 124M models

### steps

Controlled by `--steps` flag (default 30000). Total number of weight updates.
- `steps × effective_batch = total tokens processed`
- Example: 30000 steps × 2048 tokens = ~61M tokens (1 epoch for the test data)
- For 500M tokens with B=8, accum=4: need `500M / 16384 ≈ 30,500 steps`


## Quick Reference: All CLI Flags

| Flag | Default | Description |
|---|---|---|
| `data/file.bin` | `data/train.bin` | Positional arg — path to tokenized binary data |
| `--fp16` | off | Enable mixed precision (tensor cores) |
| `--checkpoint path` | none | Load weights from a saved .bin file |
| `--lr 3e-4` | 1.5e-4 | Peak learning rate |
| `--steps 30000` | 30000 | Total training steps |
| `--accum 4` | 1 | Gradient accumulation steps |
| `--warmup 1000` | 1000 | Linear warmup steps |
